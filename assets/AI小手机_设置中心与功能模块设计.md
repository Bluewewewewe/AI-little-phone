# AI小手机 — 设置中心与功能模块设计文档

> **文档版本**：v1.0  
> **更新时间**：2025年1月  
> **适用产品**：AI小手机（CP粉丝社区虚拟手机网页游戏）  
> **目标读者**：产品经理、开发团队、设计团队

---

## 📌 写在前面

本文档是AI小手机「我的→设置」页面及核心功能模块的完整设计规范。文档整合了已有的功能开关、新增的世界观/外卖/购物/家园系统，以及后台管理能力，力求覆盖从MVP到完整版的全貌。

设计原则：
- 🎮 **沉浸优先**：所有交互都要强化"这是真正的手机"的错觉
- 💕 **CP粉导向**：功能设计紧扣CP嗑糖、角色互动、情感投射三大核心需求
- 🔧 **可插拔**：世界观、外卖、购物等模块应设计为可独立开关的子系统

## 第二部分：设置中心 — 全部开关清单

> 以下开关均在「我的→AI设置」页面中管理，采用 **开关控件 + 详细说明** 的形式展示。

### 2.1 🤖 AI与对话

| 开关名称 | 用户视角说明 | 获取方式 | 开启效果 | 关闭效果 | 备注 |
|---------|-------------|---------|---------|---------|------|
| 心跳消息 | 允许角色发送心跳/想你类消息 | 免费 | 角色会主动发送暧昧、想念的消息 | 角色不主动发送心动内容 | 可配合「心跳频率」调节强度 |
| 心跳频率 | 心跳消息发送的频繁程度 | 免费（滑块） | - 低调：每天1-2次<br>- 正常：每天3-5次<br>- 高调：每天6-10次 | 不发送 | 仅心跳消息开启时生效 |
| 时间感知系统(TPES) | 角色感知现实中的时间 | 免费 | 早安/午安/晚安，不同时段说不同话，节日祝福 | 角色使用游戏内固定时间 | 核心功能，建议默认开启 |
| 主动消息 | 角色会主动找你聊天 | 免费 | 角色会不定时发消息问候、分享日常 | 纯被动响应 | 可调节频率 |
| 主动消息频率 | 主动消息的频繁程度 | 免费（滑块） | - 低：每2-3小时一次<br>- 中：每小时一次<br>- 高：每15-30分钟一次 | 不主动发消息 | 建议默认「中」 |
| 情绪波动 | 角色的情绪起伏强度 | 免费（滑块） | - 平稳：情绪变化较少<br>- 适中：正常情绪起伏<br>- 强烈：情绪易受事件影响大幅波动 | 情绪基本稳定不变 | 强烈模式可能影响对话稳定性 |
| 记忆深度 | AI记住并提及过去对话的程度 | 免费（滑块） | - 浅：记住大致话题<br>- 中：记住重要事件<br>- 深：记住大量细节并常提及 | 几乎不回忆过去 | 深模式下对话上下文会快速增长 |
| 回忆提及频率 | AI主动提及过去事件的频繁程度 | 免费（滑块） | - 偶尔：很少主动提及<br>- 适中：偶尔提起<br>- 经常：经常翻旧账/回忆甜蜜时刻 | 几乎不主动提及 | 与记忆深度配合使用 |
| 角色主动性 | 角色主导对话的意愿强度 | 免费（滑块） | - 被动：等你说话<br>- 平衡：偶尔主动<br>- 主动：经常引导话题、提问、反撩 | 角色被动等待 | 主动模式需配合主动消息 |
| 对话风格 | 角色说话的风格偏好 | 免费（选择器） | - 甜蜜撒娇：语言更亲昵可爱<br>- 日常自然：更接近真实对话<br>- 霸道宠溺：语言更强势宠溺 | - | 可选，切换后AI会调整语气 |
| 称呼偏好 | 角色的称呼方式 | 免费（选择器） | - 宝贝/宝宝<br>- 媳妇/老婆<br>- 昵称（自定义）<br>- 甜玉米/名字 | - | 需角色支持该称呼 |
| 敏感词过滤 | 过滤不当内容 | 免费 | 过滤违规、低俗内容 | 不过滤（会员专属） | ⚠️ 关闭后内容风险自负 |

### 3.4 开关控制逻辑

每个世界观的开关遵循以下逻辑：

```typescript
interface WorldviewSetting {
  // 世界观唯一标识
  worldviewId: string;
  
  // 是否已激活（通过兑换码）
  isActivated: boolean;
  
  // 是否已开启
  isEnabled: boolean;
  
  // 激活时间
  activatedAt?: Date;
  
  // 关联的兑换码
  redeemCode?: string;
}

// 切换逻辑伪代码
function switchWorldview(newWorldviewId: string) {
  // 1. 检查是否已激活
  if (!worldviewSettings[newWorldviewId].isActivated) {
    return { success: false, message: "请先激活该世界观" };
  }
  
  // 2. 关闭当前世界观
  if (currentWorldview) {
    worldviewSettings[currentWorldview].isEnabled = false;
  }
  
  // 3. 开启新世界观
  worldviewSettings[newWorldviewId].isEnabled = true;
  currentWorldview = newWorldviewId;
  
  // 4. 重置AI上下文，注入新世界观设定
  resetAIContext();
  injectWorldviewPrompt(newWorldviewId);
  
  return { success: true, message: "已进入新世界观" };
}
```

**关闭后回归现实的逻辑：**
1. 用户关闭世界观开关
2. AI上下文中的世界观设定被清除
3. 注入「回归现实」的提示词
4. 角色设定恢复到现实世界版本
5. 之前的对话记忆保留，但设定不再生效

```typescript
// 穿搭系统数据结构
interface OutfitSystem {
  // 每个角色的当前穿搭
  characterOutfits: Record<string, CharacterOutfit>;
  
  // 已拥有的服装库
  wardrobe: {
    characterId: string;
    items: WardrobeItem[];
  }[];
}

interface CharacterOutfit {
  characterId: string;
  
  // 各部位穿戴
  layers: {
    hat?: string;           // 帽子
    top: string;            // 上装
    bottom?: string;        // 下装
    dress?: string;         // 连衣裙（与上下装互斥）
    shoes: string;          // 鞋子
    accessory?: string;     // 配饰
    bag?: string;           // 包
    necklace?: string;      // 项链
    watch?: string;          // 手表
  };
  
  // 穿搭评分（系统根据搭配计算）
  styleScore: number;
  
  // 最后更新时间
  updatedAt: Date;
}

interface WardrobeItem {
  itemId: string;
  name: string;
  category: string;
  rarity: "common" | "rare" | "epic" | "legendary";
  purchaseDate: Date;
  wearCount: number;
  hasBeenWorn: boolean;
}
```

**像素小人渲染规则：**
1. 分层渲染，从内到外：身体→内搭→上装→下装/裙子→外套→配饰→鞋子
2. 连衣裙模式：隐藏上装+下装，显示连衣裙+外套+下摆细节
3. 配饰叠加：同一部位多个配饰时，显示最后添加的

## 第九部分：邀请码与反拉票投票系统

### 9.1 设计目标

在粉丝社区活动中（如创作比赛、作品投票），防止用户通过邀请关系链拉票刷票。通过邀请码构建用户关系树，计算投票人与参赛者之间的"关系距离"，据此对票数进行加权折扣——关系越近，票数权重越低。

### 9.2 邀请码系统

**核心规则：**
- 每个注册用户自动获得 **10个邀请码**
- 被邀请人注册后，记录其邀请人（`referrer_id`），形成树状结构
- 邀请关系不可更改，不可自邀（不能用自己生成的码注册）
- 邀请码可撤销/作废，撤销后已注册的用户不受影响（树关系保持不变）

**数据结构：**

```typescript
interface User {
  userId: string;
  referrerId: string | null;  // 邀请人ID，根节点为null
  inviteCodes: string[];      // 该用户持有的邀请码
  usedInviteCodes: string[];  // 已使用的邀请码
  registeredAt: Date;
  invitedBy: string;          // 使用的邀请码
}

interface InviteCode {
  code: string;
  ownerId: string;            // 生成该码的用户
  usedBy: string | null;      // 被谁使用，null=未使用
  createdAt: Date;
  revokedAt: Date | null;
}
```

**树形结构示例：**

```
根（管理员/初始用户）
├── 用户A（被根邀请）
│   ├── 用户B（被A邀请）  ← 参赛者
│   └── 用户D（被A邀请）
├── 用户E（被根邀请）
│   └── 用户F（被E邀请）
└── 用户G（被根邀请）
```

### 9.3 关系距离计算

**定义：** 两个用户在邀请树中的"树距离"= 它们之间最短路径的边数。

**计算方法：** 找最近公共祖先（LCA），距离 = 用户1到LCA的深度 + 用户2到LCA的深度。

**示例（以参赛者B为例）：**

| 投票人 | 路径 | 树距离 | 说明 |
|-------|------|:------:|------|
| A | A→B | 1 | A直接邀请了B，直系关系 |
| D | D→A→B | 2 | D和B被同一人（A）邀请 |
| 根 | 根→A→B | 2 | B的上线A的上线 |
| E | E→根→A→B | 3 | 隔了一层 |
| F | F→E→根→A→B | 4 | 弱关系 |
| G | G→根→A→B | 3 | 弱关系 |
| 不在同一子树的用户 | 无公共祖先（或仅根） | 5+ | 无关系 |

**性能说明：**
- 每次用户最多邀请10人，树深度有限（5-7层即可覆盖上万用户）
- 计算树距离：从两个用户分别往上遍历到根，记录路径，找交点
- 时间复杂度 O(树深度)，实际操作仅十几步，毫秒级完成
- 数据库仅需在用户表增加 `referrer_id` 字段，几乎零额外存储成本

### 9.4 投票权重规则

**核心原则：** 树距离越近 → 关系越密切 → 拉票嫌疑越大 → 投票权重越低。

| 树距离 | 关系类型 | 投票权重 | 逻辑说明 |
|:------:|---------|:-------:|---------|
| 0 | 同一人 | **不可投票** | 不能给自己投票 |
| 1 | 直系邀请关系 | **0.2** | 你邀请了他/他邀请了你，拉票嫌疑最大 |
| 2 | 间接一层 | **0.4** | 很可能认识（如被同一人邀请） |
| 3 | 间接两层 | **0.6** | 可能认识 |
| 4 | 间接三层 | **0.8** | 弱关系 |
| 5+ | 远关系/无关系 | **1.0** | 等同陌生人，整票 |
| 不在同一子树 | 无关系 | **1.0** | 整票 |

**规则特点：**
- 树距离天然覆盖"亲兄弟"情况：被同一人邀请的两人，距离=2，自动按0.4计票
- 绝大多数用户不在同一子树下，票数均为1.0，只有同一邀请链内的人才会被降权
- 精准打击"邀请熟人刷票"，不影响正常社区投票公平性

### 9.5 活动流程

```
1. 管理员发起创作比赛（如"最佳绘画作品奖"）
   ├── 设置奖项：第一名/第二名/第三名
   ├── 设置投票周期：如7天
   └── 公告规则（含投票权重说明）

2. 用户提交参赛作品

3. 投票阶段
   ├── 每个用户可对每个作品投票
   ├── 系统自动计算投票人与参赛者的树距离
   ├── 根据距离映射权重，记录实际计票数
   └── 实时显示得票数（可显示原始票数和加权票数）

4. 公布结果
   ├── 按加权票数排名
   ├── 公布每笔投票明细（投票人昵称、权重、实际计票）
   └── 奖金发放（按之前设计的奖金池规则执行）
```

### 9.8 注意事项

2. **隐私保护**：关系图谱仅展示昵称，不展示真实身份信息
3. **权重可调**：后期用户量增大后，可调低最大有效距离（如距离3以上即1.0整票）
4. **防自邀**：确保用户不能使用自己生成的邀请码注册新账号
5. **多活动复用**：邀请树关系一旦建立，所有活动均可复用，无需重复计算
6. **数据库无压力**：以甜玉米粉丝体量（百至千人级别），关系树数据极小，性能无瓶颈
